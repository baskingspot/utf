# Per-call overhead on short inputs, 2026-10-31

Wave 4 cut what a call costs on 16–64-byte inputs, natively and when dispatching from a generic x86-64 build. The owner decided that ReleaseSafe keeps its safety checks (`docs/slop/plan.md`, decision 5), so nothing here turns them off.

Rebased onto `c738d5d` (wave 4's transcoding); every measurement here is of these changes on `origin/main` `66fa49c`, before transcoding's, so the convert rows show this wave's dispatch alone.

- **Per call, dispatching from baseline x86-64: a median 0.87 ns over the kernel in place, from 1.51 ns; simdutf's dispatch costs 2.57 ns.** A call is now one load and an indirect call.
- **utf ÷ simdutf, geomean of the per-operation geomeans, `origin/main` → this branch** (paired in one run per level, 877 rows, `f-*/`): native 1.13 → 1.13 (16–64-byte rows 1.15 → 1.18); dispatched from baseline 1.07 → 1.10 (16–64 bytes 0.96 → 1.04); AVX2 1.52 → 1.53 (1.59 → 1.62); SSE 16–64-byte rows 1.43 → 1.48. The same runs give `origin/main` 1.13 native and 1.07 dispatched where the final baseline had 1.18 and 1.13: run-to-run on this host moves the whole level, so compare within a run.
- **Rows at 16–64 bytes under simdutf, dispatched**, outside the noise: validation, length, and base64 21 → 11; transcoding 84 → 75. Natively in those three only `Base64Encode`/`Base64EncodeUrl` at 16 bytes stay under (0.78 → 0.88).
- **Against std and Rust at the levels where they led** (`f-baseline/`, `f-sse/`): `ValidateUtf8` on 16 and 64 ASCII bytes, utf ÷ std, baseline 0.60 → 0.72 and 0.77 → 0.85, SSE 0.85 → 0.90 and 1.00 → 1.05; SSE base64 decode, utf ÷ Rust `base64-simd`, 16 bytes 0.64 → 0.75, 64 bytes 0.86 → 0.95. std's validator is an inline loop with no call at all; what is left there is our call.
- Memory: no allocation; text smaller natively and dispatched, 1 KiB larger at `x86_64_v3`/`v2`; data +488 bytes for the slots.

## Setup

- Machine: Amp orb, KVM guest, Intel Xeon @ 2.60GHz (Ice Lake server, family 6 model 106, AVX-512 with VBMI2 and GFNI), 2 cores × 2 threads, TSC at 2.6 GHz (a tick is 0.385 ns). Every timed process pinned to CPU 3; builds and tests on CPUs 0–1.
- Zig 0.16.0, ReleaseFast; simdutf 9.2.1 from nixpkgs; Rust arms from `bench/rust` built for `x86-64-v3` and `x86-64-v2` without run-time detection, as `just bench-compare` builds them.
- Harness A/Bs: `ab.sh` (here) is `just bench-compare`'s timing as a script over any set of arms: every arm a `serve` process pinned to CPU 3, each row timed on every arm back to back in an order that rotates by row and round, fresh processes every round, round 0 sizing the loops and discarded, 10 rounds of 50 ms. `summ.py` gives each row's paired median ratio with its 95% interval and marks `>`/`<`/`~` as `bench/summary.awk` does. Each run directory under `calls-20261031/` holds `raw-<arm>.txt`, the `check` output of every arm, and `summ.txt`.
- Arms: `old` is `origin/main` (`66fa49c`) unless a section says otherwise; `-n` is `-Dcpu=native` (no dispatch); `-d` is a build for baseline x86-64 that dispatches to the AVX-512 object; `-v3` and `-v2` are `-Dcpu=x86_64_v3`/`x86_64_v2` with `-Ddispatch=false`, against simdutf's `haswell` and `westmere` kernels. The final runs build the baseline arm as `just cpu=baseline bench-compare` does (`-Dcpu=baseline -Dutf-cpu=baseline`, std for baseline too).
- Per-call microbenchmark: `calls/` (`calls.zig` for this package, `calls.cpp` for simdutf): each function called out of line in a loop of 2 million calls, as the harness's arms call, on ASCII letters (valid in every format and as base64) at 0, 16, and 64 bytes, timed with `rdtsc`; a case's figure is the minimum over 15 loops, and `calls.sh` rotates the binaries for 5 rounds and keeps each case's minimum. simdutf's cases come three ways: the public function (PLT, then its dispatch: a load of the active implementation and a virtual call), `_impl` (the implementation's virtual function with the pointer already loaded), and `empty` (an empty function in a shared library: the PLT and the loop). Build: `zig build -p out-n` (native) and `zig build -p out-d -Dutf-cpu=baseline` in a copy of `calls/` beside the checkout (`build.zig.zon` points at `../repo`); `c++ -O2 -shared -fPIC noop.cpp -o libnoop.so` and `c++ -O2 -std=c++17 calls.cpp -o calls-simdutf $(pkg-config --cflags --libs simdutf) -L. -lnoop -Wl,-rpath,$PWD`.

The loop alone costs 3.9–4.7 ticks in the Zig binaries, depending on where it lands, and 7.0 in simdutf's, whose calls go through the PLT; a short kernel overlaps the loop, so a figure is a call's cost in a loop of them, not a latency, and moves by about a tick with layout. - **Dispatch per call, median over the 46 cases at 16 and 64 bytes: 3.92 ticks (1.51 ns) on `origin/main`, 2.27 (0.87 ns) now; simdutf's 6.67 (2.57 ns)** over the 12 cases with an `_impl` twin. Our dispatched call costs less than simdutf's public one in every case they share but `utf16leToLatin1` at 64 bytes (15.86 against 14.97).
- What is left of ours is the indirect call and its return; the cached-tier load, compare, and jump table are gone. Where the difference stays at 3–8 ticks, the native figure is a kernel inlined into the loop's call and specialized there, which a call into an object cannot be. Checked for `utf32WithErrors` on 64 values: a native build where it is not inlined costs 19.1 ticks, the dispatched one 17.1, inlined 8.3. So those rows measure inlining more than dispatch: `b64decode` (5.7–7.8; native also folds the alphabet and last-chunk rule into the call), `latin1ToUtf8` (7.3–7.5), `countUtf16le` (4.2).
- simdutf's 6.7 ticks are the PLT, the load of the active implementation, and a virtual call; its empty-function loop costs 7.0 against our 3.9–4.7.

## The changes, each with its A/B

Each A/B below compares the commit before the change with the change, at the levels it can affect; the run directories hold the raw rows. Rows are the harness's, 16 and 64 bytes unless named.

### Dispatch: a pointer per function (`dispatch-baseline/`)

`dispatch.call` loaded a cached tier byte, compared it, loaded a jump-table entry, jumped, and called the tier's export directly, with a first-call path (`Init`) in the same function. Now each wired function has a slot of its own (`Slot(src, f).entry`) holding a pointer to the best tier's export; it starts at a cold `resolve`, which finds the tier with `cpuid` on the first call and stores the pointer, as an ELF IFUNC would at load time. A call is one monotonic atomic load and an indirect call. Test builds that pin a tier send the call back through `resolve` when the pin changes. Also: a struct whose scalar fields fit in a word (`base64.DecodeOptions`, `EncodeOptions`) travels as one word instead of by pointer, which had it stored and reloaded, and the tier objects omit the frame pointer. Native and `-Dcpu=x86_64_v3` builds are untouched: their `bench-utf` disassembly is identical to before apart from symbol names.

Dispatched (`old-d` is `origin/main`, `new-d` this change), every 16- and 64-byte row: **geomean 1.068, 99 rows faster and none slower of 166**; utf ÷ simdutf over the same rows 0.920 to 0.982.

### Length: one masked load up to a block (`length-base64-*`)

On AVX-512, `popBlocks` (every length function and code-point count) counts an input of up to one block with `simd.loadShort` and a popcount, where it took 16-byte vectors and the scalar loop; the length mask is applied only when the zero padding would count, which is decided at compile time by running the counting function on a zero block. Arms: `old` the dispatch change, `new` with this and the next change. 16-byte rows: native 1.11–1.44× (`CountUtf16le` 1.44, `Utf8FromUtf16be` 1.33, `Utf8FromLatin1` 1.19, `Utf16FromUtf32` 1.14), dispatched 1.05–1.31×; AVX2 unchanged (geomean 1.000 over the length and base64 operations). Per call, native, 16 bytes: `countUtf8` 9.42 to 6.65 ticks, `countUtf16le` 11.60 to 5.82, `utf8FromLatin1` 8.62 to 6.65, `utf16FromUtf32` 10.73 to 5.82 (0.8–2.2 ns).

### Base64: encode's tail in one masked load

On AVX-512 the encoder's last part under 64 bytes is `permute(loadShort(...))` where it built the block from `loadPartial`'s branches; and a decode whose input ends at a block boundary returns there instead of decoding an empty block. Per call, 16 bytes: native 18.54 to 14.59 ticks, dispatched 23.97 to 18.39; in the harness `Base64Encode/random-16` 1.11× native and 1.15× dispatched, inside the noise of those runs (`length-base64-native/`, `length-base64-baseline/`). The decode early return applies to unpadded input that is a multiple of 64 characters long, which the harness has none of (its inputs are 24, 88, and 344 characters with padding); the per-call loop's 64-character decode went from 29.22 to 19.46 ticks natively.

### Validation: UTF-32 up to four blocks, ASCII 64 bytes in one load (`short-*`)

`utf32WithErrors` on 33–64 values tested four blocks at once (the first two and the last two, overlapping) and takes the position from their masks; before, it found the failing block in a group, then loaded every block of the group again, and the failing one a third time for its masks. `ValidateUtf32Err/ascii-64` (64 values, a surrogate in the last): native 9.29 to 6.26 ns (1.48×), AVX2 14.55 to 6.88 (2.09×), SSE 20.52 to 9.90 (2.20×), dispatched 11.55 to 10.68 (1.09×). The UTF-32 block is 16 values on every level, so the path is the same everywhere. `asciiWithErrors` on exactly 64 bytes is one 64-byte load and one mask on AVX-512 instead of two 32-byte halves: 5.49 to 5.0 ticks per call, no change at 48 and 63.

### Base64: decode's last block from half of it without AVX-512 (`short-sse/`, `short-avx2/`)

A last block of up to 32 characters is classified and packed from the first 32 bytes, one vector on AVX2 and two on SSE and NEON, instead of the whole block; `finish` and `packAll` take any number of vectors. The harness's 16- and 64-byte decodes end in such a block (22 characters after trimming). AVX2: 16–64-byte decodes 1.12–1.16× (MIME 64 bytes 1.00); SSE: 1.07–1.21×, 256 bytes 1.05–1.08×. Against Rust's `base64-simd` built for the same level, the paired ratios in these runs put utf at 0.89 (AVX2) and 0.77 (SSE) of Rust at 16 bytes, from 0.77 and 0.66 before, and level at 64 bytes (`f-sse/` has the final figures).

### Validation: UTF-8's long paths out of the tier objects' entries

In the AVX-512 object, `validate.utf8` pushed three callee-saved registers on entry and `utf8WithErrors` six, for their loops, so every short call saved and restored them. Where `dispatch.exported` (the tier objects), the long path is now a `noinline` function, and so is `utf8WithErrors`' scalar finish for short inputs with an error. Native builds keep both inline: there the kernel is inlined into its callers, and the out-of-line scalar finish cost native `ValidateUtf8Err/ascii-16` 2.6 ns (9.18 to 11.78 ns in `f-native/` before it went back inline, rerun in `f-native-validate/`). Their `Result` crosses as `dispatch.pack`'s scalar: returned whole from the `noinline` function it went through memory, and the caller's load of `err` from the upper half of the 16-byte store stalled (`utf8WithErrors/64` 8.3 to 27.6 ticks before the fix). Per call, dispatched: `utf8` 16 and 48 bytes 10.0 to 7.5 ticks, 256 bytes 17.5 to 15.7; `utf8WithErrors` 16 bytes 9.2 to 7.5, 64 bytes 11.7 to 10.8, 256 bytes 17.5 to 16.3. Split in native builds too, the per-call loop's native `utf8` at 256 bytes went from 13.4 to 17.5 ticks.

## Tried and dropped

- **The page-end fallbacks' constants out of the loop preheaders.** `simd.loadShort` and `storePartial` take a page-end path that needs `iota(u8, 64)` (and `loadShort` a zero vector); LLVM hoists both into the preheader of any loop that calls them, so transcoding's tail loops keep three more zmm constants live and load them on every call (seen in `utf32ToUtf16le`). Loading the iota through a hidden pointer at its use, and zeroing with a select on the length mask, removed them from the loops. Harness, native, 16–64-byte rows of every operation (`s3-native`): convert 0.990 geomean over 126 rows, every one inside its interval; nothing to show for it, so it stays out.
- **ASCII validation of exactly 64 bytes in one 64-byte load** (as `asciiWithErrors` now does): `validate.ascii` at 48 and 64 bytes measured slower in the per-call loop, and the overlapping 16-byte loads it has were chosen by measurement in wave 2.

## Findings

- **Native rows include inlining.** The harness's native arm, like the per-call loop, inlines a kernel into its wrapper; a dispatched build calls it in another object, and simdutf calls it through the PLT and a virtual call. For short kernels whose valid path is a few instructions, inlining is worth as much as dispatch costs: `utf32WithErrors` on 64 values costs 19.1 ticks out of line natively and 8.3 inlined. So "dispatched minus native" overstates dispatch on those rows.
- **Out-of-line `Result`s go through memory.** A `noinline` Zig function returning `Result` returns it through a stack slot; when the callee writes it with one 16-byte store, the caller's load of `err` from the upper half cannot forward. Return `dispatch.pack(r)` and rebuild with `dispatch.unpack`.
- **Saved registers belong to the long path.** LLVM does not shrink-wrap a kernel whose loop needs callee-saved registers, so the export saves them before its length test. Splitting the long path into its own function moves them there; in native builds the split costs a call on long inputs and the kernel is inlined anyway, so it applies to the tier objects only (`dispatch.exported`).

## For transcoding (`src/convert.zig`)

- **Saved registers on every call.** In the AVX-512 object of a dispatching build on `c738d5d` (transcoding's wave 4 merged), 23 conversions push six callee-saved registers on entry, before their length test (the checked and valid conversions out of UTF-8, UTF-16, and UTF-32, but UTF-16 to Latin-1 and the valid UTF-32 to Latin-1), `latin1ToUtf8` four, and `validLatin1ToUtf8` three, so a 16-byte call saves and restores them for a loop it never runs; `base64.decode` pushes six too. This is the transcoding orb's unattributed 1–2 ns at 16–64 bytes, or part of it. Wave 4 fixed it in `validate.utf8` (three) and `utf8WithErrors` (six): where `dispatch.exported` (the tier objects; native builds inline the kernel into its callers, long path and all), the long path is a `noinline` function, and a `Result` comes back from it through `dispatch.pack`/`unpack`, as a scalar in two registers. Returned whole, the `Result` went through memory and loading its `err` stalled, 27.6 against 8.3 ticks at 64 bytes. Count from `objdump -d` of a baseline build: the first eight instructions of each `utf_*_avx512_*` symbol.
- **Page tests.** `loadShort`'s and `storePartial`'s test is three instructions and a branch on the fast path; the page-end path's constants, which LLVM hoists into loop preheaders, were moved out of them and measured neutral on transcoding's short rows (Tried and dropped). The test itself was not timed apart.
- **Constants before the loop.** The AVX-512 kernels without a short path run their general tail loop for inputs of a block or less, so they load the loop's constants first: `utf32ToUtf16le` about 14 zmm constants, `utf16leToLatin1` 4. A straight-line path for inputs of up to one block, tested before anything else (`simd.loadShort`, the operation, `simd.storePartial`), as `latin1ToUtf16le` has, skips both. No new helper is needed for it: `length.zig`'s short counts are `simd.loadShort` plus a popcount.
- **Inlining.** In the native harness each kernel is inlined into the arm's wrapper; the dispatched one cannot be, and simdutf's never is. Several short native rows lead simdutf by what inlining saves, which a dispatched build gives back (`latin1ToUtf8` 7.4 ticks a call over native).
