# Shared SIMD helpers, 2026-10-31

Wave 2's kernel orbs each kept private copies of the same techniques: validation a masked `loadShort`, `loadAligned`, and `toBoundary`; base64 a block-ending `loadTail`, a page-safe `storePartial`, and `lowBits`; transcoding an `x512` struct with compress, `vpermb`/`vpermi2b`/`vpermi2d`, `vpmultishiftqb`, `pext`/`pdep`/`bzhi`, page-checked masked loads and stores with out-of-line buffered fallbacks, a volatile load, and `packusdw`/`packuswb` narrowing. This wave puts one set in `src/simd.zig`, moves `validate.zig`, `convert.zig`, and `base64.zig` onto it, and deletes the copies. `length.zig` had none to move (its `alignHead` returns 0 on a boundary, which its sums want; `toBoundary` returns a whole block there, which the validators want).

## The helpers

| helper                      | what it does                                                                                                                                                                  | used by               |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| `has_bmi2`, `has_masked`    | comptime: BMI2 on x86-64; AVX-512 masked loads and stores (LLVM backend only)                                                                                                 | all                   |
| `loadAligned(T, src)`       | a block from a 64-byte aligned slice, so SSE can fold it into an operand                                                                                                      | validate              |
| `toBoundary(T, p)`          | units to the next 64-byte boundary, a whole block on one                                                                                                                      | validate              |
| `loadVolatile(V, src)`      | one load per register, which LLVM may not narrow (shuffle-table entries, input windows); loads through `*align(1) const volatile V`                                           | convert               |
| `storeVolatile(dst, v)`     | one store per register, which LLVM may not split (a 64-byte store it cannot prove aligned) or merge                                                                           | available             |
| `lowBits(M, n)`             | the low `n` bits of `M`, saturating to 255: one `bzhi` with BMI2                                                                                                              | all                   |
| `loadShort(T, src)`         | up to a whole block, zero-padded, never reading past `src`: one masked load on AVX-512 (see the page rule); `loadPartial` elsewhere                                           | validate, convert     |
| `loadTail(src, start, end)` | the block that ends at `end`, moved down with `vpermb`, where a masked load would wait on stores to the bytes it masks off (an output written just after the input)           | base64                |
| `storePartial(dst, v, n)`   | the first `min(n, lanes)` lanes of a 16-, 32-, or 64-byte vector, writing nothing past them: one masked store on AVX-512 (see the page rule), else 16-byte and integer stores | base64, convert       |
| `compress(v, keep)`         | `vpcompressb/w/d`                                                                                                                                                             | convert               |
| `permute(table, idx)`       | `vpermb`                                                                                                                                                                      | convert, base64, simd |
| `permute2(lo, idx, hi)`     | `vpermi2b` for bytes, `vpermi2d` for 32-bit lanes (LLVM picks `vpermt2*` when the table register is the one overwritten)                                                      | convert, base64, simd |
| `multishift(ctrl, data)`    | `vpmultishiftqb`                                                                                                                                                              | base64                |
| `pext`, `pdep`              | BMI2                                                                                                                                                                          | convert               |
| `narrow(To, v)`             | 32-bit lanes to `u16` or `u8`: `packusdw` (+ `packuswb`), with a `vpermq` on AVX2 to undo the per-lane order; a truncation elsewhere                                          | convert               |

Not shared, because one module uses them: base64's `pmaddubsw`/`pmaddwd`/`pmulhuw` helpers and its whitespace ring, transcoding's shuffle tables, `storeWidened`, and `firstStep`, and length's `alignHead`.

### The page rule

A masked load or store whose masked-off bytes fall on a page that is unmapped, or mapped but never written (a fresh output buffer, or the page after a short input), takes a microcode assist on every call. Measured with [masked-assist.zig](simd-wave3-20261031/masked-assist.zig) on this machine: a 16-byte masked load within a page costs 2–2.6 cycles, the same load with its masked-off rest on an untouched page about 240.

So `loadShort` and `storePartial` stay masked only when that cannot happen:

1. The common case in one test: all 64 bytes on one page (`addr % 4096 <= 4032`).
2. Else, if the masked-off bytes are on the page of the last counted byte (`restOnPage`), still masked.
3. Else the data starts in the last 63 bytes of its page, so the 64 bytes that _end_ where the data does lie on that page, which is the data's own page: with VBMI the access goes in as the end of those 64 bytes, moved with `vpermi2b` (load) or `vpermb` (store), still one masked access. Without VBMI, `loadPartial` or the 16-byte and integer stores.

No call, no saved registers, no stack buffer. Transcoding's old fallbacks were `noinline` and went through a 64-byte stack buffer; an out-of-line fallback added saved registers to every leaf validator that inlined `loadShort` (−20% at 16 bytes), and an inline `loadPartial` fallback did the same to `utf32WithErrors`, so both were rejected for rule 3. Validation's old private `loadShort` had no page check at all, which is the bug below.

The first test is what transcoding's `x512` had; the first version of the shared helpers used only `restOnPage`, which needs the byte length (`min(n, lanes) * size`) and a byte mask before the test. In the UTF-8 to UTF-16 and UTF-32 decode loop, with up to four stores per block, that cost 7–15% on Arabic, Hebrew, Russian, and Hindi text (`first-native-convert-benchstat.txt`, that version against `old`); with test 1 first and a mask per lane (`vmovdqu16/32`) those rows came back (Hebrew UTF-8 to UTF-16BE +9%).

### Short validation next to a page edge (a fix)

Validation's wave-2 `loadShort` masked every short input. [short.zig](simd-wave3-20261031/short.zig) calls the `WithErrors` and bool validators out of line on 7–63 byte inputs, either 16 bytes past a 64-byte boundary (`mid`) or ending one byte before a page whose next page is mapped and never touched (`edge`). ns per call, median of 8 interleaved rounds:

```
row                    old     new
utf8/edge/size=7     102.2     6.9
utf8/edge/size=16    113.3     6.5
utf8Err/edge/size=33 125.7     7.2
utf16le/edge/size=16 106.7     4.2
utf32/edge/size=48   138.4     4.6
utf32Err/edge/size=48 139.4    4.2
utf8/mid/size=16       5.9     6.2
utf8Err/mid/size=16    6.3     6.6
utf8Err/mid/size=48    6.5     7.1
utf16le/mid/size=16    3.8     3.8
utf32/mid/size=63      3.6     3.9
```

Every `edge` row 15–33× faster (98–142 ns to 4–7 ns); size 63 never reached the next page. The `mid` rows are level except UTF-8 at 16–48 bytes, 0.3–0.6 ns slower (−5 to −8%, p = 0.02–0.05): the page test is one `and`, `cmp`, and branch before the mask. Full table: `short-benchstat.txt`.

## Measurements

- Machine: Amp orb, KVM guest, Intel Xeon @ 2.60GHz (Ice Lake server, family 6 model 106, AVX-512 with VBMI, VBMI2, and GFNI), 2 cores × 2 threads; every timed process pinned to CPU 3, builds on CPUs 0–1. Zig 0.16.0, ReleaseFast.
- Arms: `old` is `9b0ddba` (origin/main `b9565a3` plus the dispatch fix, [dispatch-wave3-20261031.md](dispatch-wave3-20261031.md)), `new` this change. Both built against the same harness (wave 3's, `Out` built from scalars).
- The harness A/B, [hrun.sh](simd-wave3-20261031/hrun.sh): `bench-utf bench <every op in bench/ops.tsv>` for each arm, the arm order rotated each round, pinned to CPU 3; benchstat over GB/s. Arms built with [hb.sh](simd-wave3-20261031/hb.sh): native (`-Dutf-cpu=native`, no dispatch, the AVX-512 kernels), dispatched (`-Dutf-cpu=x86_64_v3`, the package default for that CPU: runtime dispatch, which picks the AVX-512 tier here), and AVX2 (`-Dutf-cpu=x86_64_v3 -Dutf-dispatch=false`).
- Base64 also through its wave-2 driver ([base64-20261031/driver.zig](base64-20261031/driver.zig), old tree as `old`), whose paired samples are tighter than the harness's base64 rows: 10 samples, encode, decode, LF and CR LF lines, and `ADJACENT=1` (output right after the input).
- Calibration: the harness's rows move with code layout. `length.zig` is unchanged and its code is identical between the arms (diffed), yet native `CountUtf8` reads −7 to −13% and `Utf16FromUtf32` +12 to +22%, all with p < 0.05. A row is a regression here only when it moves past that and its function's code changed in a way that explains it.

### AVX2 and SSE UTF-16 to Latin-1 under 32 units

The harness orb found AVX2 `utf16le/beToLatin1` taking 15.7–20 ns on 16 code units against 7–11 at 64. The AVX2 and SSE path narrowed 64- and 32-unit blocks and left the rest, up to 31 units, to the scalar loop. Now the last 1–31 units go in two 16-unit vectors, the second ending at the input's end (rewriting some bytes already narrowed), with one range test over both; an error anywhere in them still goes to the scalar code, which finds its position. A first version with a 16-unit step and then the overlapping vector cost 7–26% at 64–256 units (`lat-first-version-benchstat.txt`): its conditions added a saved register to every call; the final one has the old function's two.

Harness, AVX2 build (`-Dutf-cpu=x86_64_v3 -Dutf-dispatch=false`), 8 rounds, the four ops, this change alone (`lat-benchstat.txt`):

```
row                               before   after  (ns per call)
Utf16leToLatin1/latin1-16          13.4     5.8
Utf16beToLatin1/latin1-16          12.9     6.2
ValidUtf16leToLatin1/latin1-16      6.7     5.1
ValidUtf16beToLatin1/latin1-16      6.5     4.9
Utf16leToLatin1/latin1-64           5.5     5.9
```

Checked 2.1–2.4×, valid 1.3× at 16 units; from 256 units level, at 64 units LE −7 to −9% (p = 0.02–0.04; 0.4 ns), BE level. Geomean over the four ops +7.8%.

### Code size and memory

No allocation, no new stack use. Text of the audit binary, which references every public function: native 120,150 to 109,558 bytes, dispatching baseline 922,041 to 914,457. Instructions in the public functions, native: 22,620 to 21,838. The fixed-ratio conversions lost their stack frames, and `utf8ToUtf32` uses the stack 4 times instead of 98 (`validUtf8ToUtf32` 0 instead of 94): the buffered fallbacks and their frames are gone. [scan.sh](dispatch-wave3-20261031/scan.sh) finds no 16-byte `Result` copy in any public function.
