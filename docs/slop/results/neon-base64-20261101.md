# Base64 on NEON, 2026-11-01

`base64.encode` and `base64.decode` on aarch64 against simdutf's `arm64` kernel. Before this change the NEON kernel was the generic 16-byte one with `tbl` swapped in: encode 0.61 of simdutf, decode 0.83–0.94 (run 41312568501 of `bench.yml`, 10 rounds, at `25ccea6`).

- Machine: GitHub `ubuntu-26.04-arm` runner, ARM Neoverse-N2, 4 vCPUs, a shared VM ([final/lscpu.txt](neon-base64-20261101/final/lscpu.txt)). Zig 0.16.0 ReleaseFast `-Dcpu=native`, simdutf 9.2.1 (`kernel arm64`), Rust `target-cpu=native`, Go 1.26.
- Method: `.github/workflows/bench.yml`, which runs `just base=<rev> bench-compare <rounds>` over the seven base64 operations; `base` is `bench-utf` built from another revision and timed in the same rounds. The experiments ran 3 rounds each, against the state before them; the final run ran 10 rounds against `1476ab0` (main before this change) as GitHub run 41318221233, on `8366974`, whose `src/` is this commit's but for line wrapping (the aarch64 and x86-64 assembly of `encode` and `decode` are the same). Every run's checksums matched simdutf's.

## What changed, and what each step measured

Only `isa == .neon` code changed: the x86-64 assembly of `encode` and `decode` (standard and URL alphabets) is the same as `1476ab0`'s at `baseline`, `x86_64_v2`, `x86_64_v3`, `x86_64_v4` with VBMI and VBMI2, and `native` on the orb (`zig build-obj -femit-asm -fstrip`, compared after renumbering anonymous symbols), so x86 was not benchmarked.

1. **Structured loads and stores** ([loops/](neon-base64-20261101/loops/), run 41316231810, `97834f2` against `1476ab0`): encode 1.65, decode 1.22–1.23, MIME 1.12. Encode loads 48 bytes with `ld3`, makes the four indices with shifts within lanes, looks each up in the 64-character alphabet with one `tbl` from four table registers, and stores with `st4`: simdutf's loop. Decode loads each clean block with `ld4`, which puts the first, second, third, and fourth character of every chunk in a vector of its own; classification works per byte, so the de-interleaved vectors classify as they are, and packing is three shifts and ors and an `st3`. A block with a byte outside the alphabet falls back to the ordered `classifyBlock`, which gives positions. simdutf instead copies each classified block to a buffer and loads that with `ld4`; this path skips the round trip. LLVM's interleaved-access pass makes `ld3`, `st4`, `ld4`, and `st3` from a plain whole-vector load or store and strided `@shuffle`s of it, so no intrinsic is needed (and Zig cannot declare `llvm.aarch64.neon.ld4`: its struct return does not lower to the intrinsic's type, "Intrinsic has incorrect return type"). Two caveats: a volatile access is not matched, and in a test file where the fourth lane only fed an `or` whose result was joined with zeros for the 48-byte interleave, instcombine widened that lane's shuffle and LLVM emitted `tbl`s instead of `ld4`; in the kernel the fourth lane goes through a lookup, then `sli`, and stays an `ld4`.
2. **Tails** ([tails/](neon-base64-20261101/tails/), run 41316747045, `211ee9d` against `1476ab0`): MIME 1.12 → 1.19, the rest unchanged within noise. The 12-byte encode step that finishes an input shifts each 16-bit lane by its own count (`ushl`) where the generic code multiplied, and looks up with the four-register `tbl`: 8 instructions for 12 bytes. `packWords` on little-endian NEON combines pairs in 16-bit lanes and then 32-bit lanes with one shift each way, 8 instructions where the generic form takes 10; it packs every partial block and short input.
3. **`sli` in the decode pack** ([sli-decode/](neon-base64-20261101/sli-decode/), run 41316792294, against `211ee9d`): decode 1.04, URL 1.04, strict 1.05, partial 1.04, MIME 1.01. `vsli` from `llvm.aarch64.neon.vsli.v16i8` packs a block in 5 instructions where LLVM made 8 from the shifts and ors.
4. **`ushr` and `sli` in the encode loop** ([sli-encode/](neon-base64-20261101/sli-encode/), run 41317272819, against `1ceeef8`): encode 1.03, 1.053–1.055 from 4 KiB (URL 1.055–1.060), which took it from 0.95 to 1.00 of simdutf there. LLVM had made the middle indices with `shl` and `usra`; disassembling nixpkgs' aarch64 libsimdutf 9.2.1 showed simdutf's loop to be ours instruction for instruction except `ushr` and `sli` in their place. `usra` is a shift-accumulate, which Arm's Neoverse optimization guides list with more latency than `sli` on the same shift pipe; the 5% is measured, the reason is not.
5. **Short tails with whitespace** ([spaced-tail/](neon-base64-20261101/spaced-tail/), run 41317407616, `30918f8` against `1ceeef8`): MIME 64 B 1.28 (0.79 to 1.01 of simdutf), MIME geomean 1.04, decode 1.00. A last block of up to 32 characters is classified as two vectors; when it holds whitespace (MIME's last line break), the whitespace is removed and the rest decoded from those two vectors, where the block was classified again as four. `compressVec`, `shiftFrom`, and `finishSpaced` take vectors of any count for it.
6. **`add` for the roll slot** ([slot-add/](neon-base64-20261101/slot-add/), run 41317660458, `5684fa5` against `8636af2`): decode and strict 1.025 from 4 KiB (partial was not in this run); URL, whose slot is an `or`, 0.997; 64 B rows 0.97–0.985, within what the 64 B rows moved where their code did not change (decode 64 B read 1.047 in step 5). LLVM folded the classifier's `hi + mask` into `usra`, redoing the shift the high-nibble lookup had done; an empty `asm` on `hi` keeps it an `add`.

Raw output for each step is in its directory (`summary.txt`, `rows.txt`, `config.txt`).

## Tried and dropped

- **Encode unrolled to 96 bytes a step** ([unroll-encode/](neon-base64-20261101/unroll-encode/), run 41316819830, against `211ee9d`): 1.00 and 0.99.
- **A MIME line's end from the block already classified** ([line-end/](neon-base64-20261101/line-end/), run 41317746722, against `8366974`): where a run of characters ends 32 or fewer characters into a block, packing that block's first one or two vectors instead of decoding the 64 characters that end there: MIME 64 B and 256 B 1.01, 4 KiB and up 0.99, decode 0.98–1.00.

## Left

- MIME 256 B is 0.93 of simdutf (0.79 before): its first line costs a failed two-block step, an ordered classification, and the line-end block, and its last 40 characters go through `finish` on four vectors.
- Encode at 256 B is 0.98–0.99: the 16 bytes after the five 48-byte steps go through the 12-byte step and the scalar tail.
- The staged path (`decodeStaged`, whitespace not in regular lines) still packs its blocks from the ring with `packBlock`; packing them with `ld4` from the ring, as simdutf does from its buffer, would apply, but no harness row takes that path.
- Not checked against simdutf with `just oracle`, which runs on the host's kernel (x86-64); the NEON paths are held to the scalar reference by the package's tests under qemu-user, little- and big-endian.
