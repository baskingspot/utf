# base64.decode in place, 2026-11-01

`base64.decode(buf[0..maxDecodedLen(n)], buf[0..n], .{})` gave wrong bytes or a spurious error when the input had whitespace, on every kernel; simdutf's `base64_to_binary` allows it, and Ghostty's Kitty graphics parser decodes line-wrapped payloads in place. The fix, and what it costs callers who decode into a buffer of their own and callers who decode in place.

- Machine: Amp orb, KVM guest, Intel Xeon @ 2.60GHz (Ice Lake server, family 6 model 106, AVX-512 with VBMI2), 4 vCPUs ([lscpu.txt](base64-in-place-20261101/lscpu.txt)); every timed process pinned to CPU 3, nothing built while anything was timed. Zig 0.16.0 ReleaseFast, simdutf 9.2.1.
- Separate buffers: `just cpu=<cpu> [dispatch=false] base=main bench-compare 30 base64-decode base64-decode-strict base64-decode-mime`, the fix in the working tree on `25ccea6` against `bench-utf` built from `25ccea6`, timed in the same rounds: [avx512](base64-in-place-20261101/avx512/) (`cpu=native`), [avx2](base64-in-place-20261101/avx2/) (`cpu=x86_64_v3 dispatch=false`), [sse](base64-in-place-20261101/sse/) (`cpu=x86_64_v2 dispatch=false`). Ratios are utf ÷ base from `rows.txt`, median of 30 per-round ratios with the 95% interval; above 1 the fix is faster.
- In place: the harness has no in-place operation, so [in-place/bench.zig](base64-in-place-20261101/in-place/bench.zig) times it: the corpus's shapes (random bytes, standard padded base64, unwrapped and in 76-column lines ending CRLF) at 16 B to 1 MiB, three arms per row in a rotating order, each copying the input into a work buffer first, since decoding in place consumes it: `Copy` alone, `Separate` (copy, then decode the copy into another buffer), and `InPlace` (copy, then decode the copy over itself). Built with `zig build-exe -OReleaseFast -fllvm -mcpu=<cpu> --dep utf -Mroot=bench.zig --dep dispatch_options -Mutf=<tree>/src/root.zig -Mdispatch_options=opts.zig` from this tree (`fixed`) and from `25ccea6` (`base`), at `native`, `x86_64_v3`, and `x86_64_v2`; ten rounds, a fresh process per build and round, alternating which build goes first ([run.sh](base64-in-place-20261101/in-place/run.sh)); `bs-<cpu>.txt` is benchstat's base against fixed.

## Takeaways

- **The cause**: the guess was close. Not the staging ring, which decodes 256 values behind its reads, but the regular-lines path (wave 3) reloads `src` after writing `dst`. The block that ends a run of characters is decoded again from `src[end - 64 .. end]`, overlapping what the run's earlier blocks wrote; in place, the first line's earlier block has already overwritten those bytes (76-column input: the reload starts at byte 12, and `dst[0..64]` was written). `decodeLines` reloads the same way at each line's end on AVX-512, and when it stops at a bad line, `decodeBlocks` starts again at that line, whose start the stopped line's stores may have overwritten. The scalar decoder, the staging ring, and the clean-block loop already read each byte before anything writes it.
- **The fix**: `untouched(dst, src, i, n)`, true unless `dst` starts at `src` and `n > i`, guards both reloads. The block that ends a run reloads from `src` only when the stores so far (`o + slack`) end before it; otherwise it decodes the run's end from the block it already classified and stores exactly `p / 4 * 3` bytes, no slack, which would overwrite the characters after the run. `decodeLines` starts only when a whole line's stores (`lineVectors(len) / 4 * 3 + slack`) end before the line's start. In place, each line moves its start further ahead of its output (by `len / 4 + k`: 21 bytes for MIME lines), so the check holds for every later line and for the restart, and MIME lines from the fifth on run in `decodeLines`. Separate buffers take both checks as one pointer compare each.
- **Callers with separate buffers: no change outside the noise**, short and line-wrapped inputs included. Geomeans utf ÷ base: AVX-512 decode 1.02, strict 1.00, MIME 1.03; AVX2 0.99, 1.00, 0.98; SSE 1.00, 1.01, 1.00. The 16-byte rows (24 characters) never reach the changed code and read 0.98–1.09. One row repeats below 1: **AVX2 MIME 256 B, 0.96** [0.94, 1.00] here and 0.95–0.96 in three earlier runs of the fix's variants, about 2 ns of a 50 ns call; a 344-character input takes both checks once and has only three lines to spread them over. The same row is 0.99 on AVX-512 and 1.00 on SSE.
- **Callers decoding in place now get the right answer**, and pay for it on short line-wrapped input. The base build returned wrong output in place on every MIME row from 256 B (every sample flagged it), so its in-place times there are of a decode that stopped early. Fixed, `InPlace` against `Separate` on MIME lines (ns a call, copy included in both):

  | MIME input | AVX-512 in place | separate | AVX2 in place | separate | SSE in place | separate |
  | ---------: | ---------------: | -------: | ------------: | -------: | -----------: | -------: |
  |       16 B |             18.5 |     18.9 |          18.4 |     18.1 |         16.2 |     16.2 |
  |       64 B |             39.1 |     26.3 |          31.9 |     32.0 |         28.8 |     28.7 |
  |      256 B |             81.0 |     46.4 |          78.2 |     48.0 |        103.9 |     67.3 |
  |      4 KiB |              440 |      385 |           509 |      446 |          691 |      626 |
  |     64 KiB |            8 630 |    9 250 |         9 020 |    9 050 |       10 730 |   10 680 |
  |      1 MiB |          205 800 |  229 100 |       208 400 |  237 100 |      239 400 |  269 800 |

  At 256 B (four lines) no line is far enough ahead to use `decodeLines`, so every line takes `decodeBlocks`' block-at-a-time path, which classifies the block ending each line two or three times; 30–37 ns more a call. At 4 KiB the first four lines do not, 10–15% more. From 64 KiB it is level or ahead (the input is already in cache from the copy).

- **AVX-512 in place pays about 12 ns a call on any input of 64 characters or more with a partial last block**, line-wrapped or not, and did before the fix: unwrapped 64 B (88 characters) takes 30.7 ns in place against 19.0 into another buffer (base: 32.6 against 20.1), MIME 64 B 39.1 against 26.3. `simd.loadTail` with VBMI loads the 64 bytes that end at the input's end, which in place cover the bytes the previous block just stored, and the load cannot be forwarded from those stores. AVX2 and SSE build the tail from narrower loads and show nothing (AVX2 unwrapped 64 B: 19.6 in place, 20.6 separate). Not fixed here.
- **Rejected**: the in-place fallback out of line (`noinline` with a pointer to the classified block). It spills the block to the stack on every path: AVX2 MIME 4 KiB to 1 MiB 0.92–0.96 of the inline fallback ([rejected-out-of-line](base64-in-place-20261101/rejected-out-of-line/)). A range test for any overlap (`d + n <= s + i or d >= s + src.len`) measured the same as the pointer compare; the pointer compare is what the documented contract needs.
- **Memory**: nothing allocates, and peak RSS is unchanged (`rss.txt` in each run).

## Correctness

The kernel tests' `expectSameDecode` and the dispatched `publicCases` now decode every input into a buffer of its own and in place, and expect the scalar reference's result and bytes from both. With the fix reverted, four tests fail; with only the run-end guard, three; with `decodeLines` allowed in once the next 64 + slack bytes are behind (not a whole line), the regular-lines test still fails. A scratch differential run of 200 000 inputs (valid, corrupted, and truncated; padded and not; up to 3000 bytes; 5 or 0–2 random whitespace characters, or lines of 1–300 characters with one of five gaps; random room) against the scalar reference, separately and in place, on every kernel and through `decode`, found no mismatch at `native` (generic, SSSE3, AVX2, AVX-512 VBMI), `x86_64_v3`, `x86_64_v2`, `baseline` (ReleaseSafe), and Debug; on the unfixed code the same run found 45 661 wrong results across the kernels and `decode`.
