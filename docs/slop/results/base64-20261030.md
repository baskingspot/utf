# Base64: SIMD encode and decode, 2026-10-30

The first `src/base64.zig`: Muła and Lemire's AVX2 and SSSE3 encode and decode, a generic `@Vector` kernel, a NEON variant of it, whitespace-forgiving decode, and the scalar reference in `src/scalar_base64.zig`. Measured against simdutf, Zig's std, Rust's `base64-simd`, and Go with `just bench-compare`, and kernel by kernel, with whitespace, by the driver in [base64-20261030/driver.zig](base64-20261030/driver.zig).

- Machine: Amp orb, KVM guest, Intel Xeon @ 2.60GHz (Ice Lake server, AVX-512 with VBMI2), 4 vCPUs. Zig 0.16.0 ReleaseFast for the host CPU, so `encode` and `decode` use the AVX2 kernel; simdutf 9.2.1 with its runtime dispatch (`icelake`, AVX-512) unless pinned.
- Commands: `just bench-compare 6 base64-encode base64-decode` on commit `base64: encode and decode with SIMD kernels and a scalar reference` (rebased on 2acc1ee); then the driver, 10 interleaved samples per arm pinned to CPU 2, and 5 more with `SIMDUTF_FORCE_IMPLEMENTATION=haswell` and `westmere` for simdutf's AVX2 and SSE kernels. Raw output in [base64-20261030/](base64-20261030/): `raw-*.txt` from the harness, `final-*.txt` from the driver.
- Throughput is input bytes: binary bytes for encode, base64 characters for decode. Compare within one table only; simdutf's base64 rows move up to 44% between runs on this orb.

## Takeaways

- Against the same instruction set, the AVX2 kernel matches simdutf's `haswell` on encode (18.3 vs 17.5 GB/s at 64 KiB) and trails it by 5–15% on decode from 4 KiB up (17.8 vs 18.7 at 4 KiB, 16.8 vs 19.8 at 64 KiB); below 1 KiB it leads both ways (encode 11.8 vs 7.5 at 256 bytes, decode 9.5 vs 6.3). SSSE3 matches `westmere`: 9.6 vs 9.5 encoding, 9.4 vs 9.2 decoding at 64 KiB.
- Against simdutf's best kernel here (`icelake`, AVX-512 VBMI), we trail from 256 bytes up: 17.1 vs 41.3 GB/s encoding 4 KiB and 16.5 vs 43.6 decoding 64 KiB in the harness run. Closing that is the AVX-512 VBMI kernel, wave 2. At 1 MiB, where memory bandwidth limits both, we are level or ahead (encode 12.7 vs 11.2).
- Short inputs, harness run: encode 16 bytes 1.55 GB/s to simdutf's 1.91 and Rust's 1.88; 64 bytes 4.95 to 6.39. Decode 16 bytes 1.15 GB/s, ahead of simdutf (1.13) and behind std (1.60) and Rust (1.68); 64 bytes 3.46, level with simdutf (3.51), behind Rust (4.53). The gap at 16 bytes is the padded last chunk: decoding 24 characters with `==` costs about 4 ns more than without, in the scalar finish. Not yet the best arm on those rows.
- Whitespace (base64 in 76-character lines, as MIME writes it): AVX2 7.2 GB/s at 64 KiB to simdutf `haswell`'s 10.3 and `icelake`'s 14.2; std's ignoring decoder does 0.37. The generic kernel, which has no byte shuffle, does 3.4.
- Every utf row beats std and Go by 2.8–16× from 64 bytes up, and `base64-simd` by 1.4–1.9× from 4 KiB up.
- Memory: no allocation. Peak RSS equals std's, 3.3 MiB, the inputs and buffers. Decoding uses 336 bytes of stack for whitespace staging.

## What moved the numbers

Each step below was measured with the driver, one interleaved sample per arm, and kept only if it helped; the numbers are GiB/s at 4–64 KiB as benchstat printed them then, and the tables further down are the final state.

- Kernel functions `inline`, and lookup constants forced comptime: AVX2 encode 1.8 to 12 GB/s. Without it LLVM called the kernel per vector and built shift-amount vectors byte by byte at run time.
- The encode load is volatile: AVX2 encode 12 to 16.5 GB/s. LLVM narrows a 32-byte load whose first and last 4 bytes the shuffle does not use into three loads and two permutes; volatile keeps one load, which is Muła and Lemire's load from 4 bytes early.
- Decode stores whole vectors, volatile, each overwriting the slack of the one before: AVX2 decode 13.5 to 17 GB/s. LLVM merges two adjacent 24-byte stores with nine shuffles; volatile keeps the paper's `vpshufb` and `vpermd` per vector.
- Whitespace: classify each block once and stage 6-bit values, not characters (2.9 to 4.1 GB/s); decode the stage four blocks at a time, after the stores retire (4.1 to 4.9); remove one or two whitespace characters by shifting the block down a lane instead of the table compress (4.9 to 7.1). Doing exactly two removals without a branch was slower (6.2), since 76-character lines put at most one break in a 64-byte block.
- Scalar decode: per-position 32-bit tables for four characters at a time, std's technique, and a tight loop for whole chunks: 1.7 to 2.5; it decodes inputs under 64 characters, with one 16-character SIMD step first.

## Correctness

- `src/scalar_base64.zig` matched simdutf 9.2.1's `base64_to_binary` on 115 million inputs before any SIMD existed: every string up to 8 characters over `ABQ= *\n-` in both alphabets and all three last-chunk modes, and 900,000 random encodings with whitespace, padding, and invalid bytes mutated in. Error kinds and positions included. The rules it encodes: trailing whitespace and up to two `=` are cut first, `invalid_base64_character` points at the character or at the first cut `=`, `base64_input_remainder` and `base64_extra_bits` at the end of the data before the padding.
- Each SIMD kernel is tested in one build against the scalar reference: every byte value at every position of a two-block input, whitespace and invalid bytes inserted and replacing at every position for lengths around one, two, and three blocks, line-wrapped and space-strewn input in every last-chunk mode with random short output buffers, and encode of every length to 600 bytes against scalar and `std.base64`. Kernels by build: native and `-Dcpu=x86_64_v3` ReleaseSafe run generic, SSSE3, and AVX2; `x86_64_v2` runs generic and SSSE3; `x86_64` runs generic; `-Dtarget=aarch64-linux -fqemu` (qemu-user from nixpkgs) runs generic and NEON, in Debug and ReleaseSafe. Debug builds on x86 use the self-hosted backend, which cannot lower LLVM intrinsics, so they run only the generic kernel.
- `just oracle 300000`: `base64.decode` 75,000 compared, 0 mismatches, under simdutf's `icelake` and `fallback` kernels. A scratch fuzzer against simdutf's C API (not committed; the oracle is the kept tool) also passed with the binary built for native, `x86_64_v2`, and `x86_64`, so the AVX2, SSSE3, and generic kernels each met simdutf directly.
