# NEON lane masks, and a first look at aarch64, 2026-11-01

The first aarch64 numbers this package has: a quick `bench-compare` on a GitHub-hosted Neoverse N2 against simdutf's `arm64` kernel, and an A/B of `simd.bitmask` on NEON.

- Machine: GitHub `ubuntu-26.04-arm` runner, ARM Neoverse-N2, 4 vCPUs, a shared VM ([fixed/lscpu.txt](neon-20261101/fixed/lscpu.txt)). Zig 0.16.0 ReleaseFast `-Dcpu=native`, simdutf 9.2.1 (`kernel arm64`), Rust `target-cpu=native`, Go 1.26.
- Method: `.github/workflows/bench.yml`, which runs `just base=25ccea6 bench-compare 3` over ten operations: `validate-utf8 validate-utf16le utf8-to-utf16le utf16le-to-utf8 utf8-to-latin1 latin1-to-utf8 utf8-from-utf16le count-utf8 base64-encode base64-decode` (128 rows). `base` is `bench-utf` built from `25ccea6` (main before this change), timed in the same rounds as every other arm. Three rounds, not ten, for a quick read; the ratios' intervals are over those three. Runs: [first](neon-20261101/first/) (GitHub run 41313453029, `abbdbff`) and [fixed](neon-20261101/fixed/) (run 41314388602, `a0b48c6`).

## Takeaways

- **Where aarch64 stands** (fixed run, utf ÷ simdutf `arm64`): 1.20 over the ten operations. Ahead: UTF-16 validation 1.84, Latin-1 to UTF-8 1.63, `countUtf8` 1.52, UTF-8 to Latin-1 1.31, UTF-8 to UTF-16 1.17, UTF-16 to UTF-8 1.14, `utf8FromUtf16le` 1.13. Under: **UTF-8 validation 0.73** (13 of 15 rows; Rust's `simdutf8` is ahead of us too, utf 0.68 of it; worst `ascii-256` 0.56), **base64 encode 0.61** (`random-65536` 0.47), base64 decode 0.89, UTF-16 to UTF-8 on Chinese 0.75, and `countUtf8` at 64 ASCII bytes 0.40. None of the AVX-512 or AVX2 tuning reached these paths; they are the generic 16-byte code with `tbl` lookups.
- **`simd.bitmask` on NEON: 1.01 overall, UTF-8 to UTF-16 1.07** (1.11–1.14 on every non-ASCII text, emoji 1.11), UTF-16 validation 1.02 (emoji 1.32), the other eight operations 0.99–1.00. LLVM lowers a bool-vector `@bitCast` with an `and`, `ext`, `zip1`, and `addv` per 16 lanes (26 instructions for 64 lanes, four `addv`); masks of 32 and 64 lanes now take each lane's bit and add neighbouring bytes with `addp`, as simdutf does (9 instructions for 64 lanes, 6 for 32 from 16-bit compares, where LLVM had also spilled to the stack). 16 lanes keep LLVM's lowering, as do big-endian targets.
- **A joined bool vector undoes it.** The first run read UTF-16 to UTF-8 at 0.87 of `base`: Korean and Hindi 0.45, Japanese 0.68, Chinese 0.87. `utf8FromBmp` built its 32-lane mask from `@bitCast([2]@Vector(16, bool){ lt80, lt800 })`; LLVM materializes that as an integer, and the `@select` in the new path took it back to lanes one `sbfx`/`mov` at a time (99 instructions against 28). Two 16-lane masks, shifted together, fix it (fixed run: 1.00, Korean 0.998), and compile to the same code as before on x86-64 at every level (LLVM folded the two forms into one function). Build a mask from one compare, not from bool vectors joined after the fact.
- Rows under 0.98 of `base` in the fixed run: `countUtf8/ascii-16` 0.94, `utf8ToLatin1/latin1-64` 0.96, and UTF-16 to UTF-8 at 16 and 64 ASCII units 0.98. Short rows whose paths use only 16-lane masks; within the layout noise the x86 waves saw (identical code moved ±15%).
- Memory: unchanged; no path allocates, and peak RSS is in [fixed/rss.txt](neon-20261101/fixed/rss.txt).

## Left

A full ten-round run of every operation on this runner is the baseline to take next.
