# UTF-8 to UTF-32 on Apple Silicon, for terminal text, 2026-11-05

Ghostty is moving its UTF-8 to UTF-32 decoding from simdutf to this package, and macOS is its main aarch64 platform. This is work on `utf8ToUtf32` for the text a terminal sees, mixed scripts, emoji, and CJK, beyond the restored baseline: `origin/main` (`026ba6b`, v0.2.2) with the three Zig 0.17 workarounds from `zig-0.17` cherry-picked (`8bc7ac2`, `eb10f9c`, `7d9f4b5`; `82f0d93` here), which another thread is landing on `main`. It also fixes a bug on `main` that the oracle found on the Mac: missed errors after three-byte characters.

- Machine: Apple M4 Pro (Virtual), a Mac satellite of 6 cores, macOS 27.2. Zig 0.17.0 ReleaseFast for `aarch64-macos` with the native CPU (`apple_m4`); simdutf 9.0.0, the copy Ghostty vendors (Ghostty `e95bed6`, `kernel arm64`), compiled by `zig c++` in the same build. Zig 0.16.0 numbers below come from the same harness with the utf shims built by Zig 0.16 (its bundled libc++ does not build against the macOS 27 SDK, so the C++ side and the link use Zig 0.17).
- Harness: [harness/](apple-utf32-20261105/harness/), [neon-apple-20261101](neon-apple-20261101.md)'s, one process holding simdutf and three builds of utf (`base`, `new`, `alt`), each a shim of Ghostty's `DecodeUTF8` (`src/simd/vt.cpp`: convert, and on an error count the valid prefix, emit U+FFFD, skip the maximal subpart, go on), with an output of one code point per input byte. Each round times every row on every arm back to back, rotating the order; `ratio.py` gives the median over rounds of each round's ratio, with the range. To rebuild it, put Ghostty's `simdutf.cpp` and `simdutf.h` beside it and utf trees at `../base` and `../alt`; the macOS commands are those of the earlier write-up. In the final run `base` is `82f0d93`, and `new` and `alt` are both this series, so `new ÷ alt` is the noise: geomean 1.003 over the 63 UTF-32 rows.
- Inputs: added to the harness, text as `ghostty-gen +utf8` (`src/synthetic/Utf8.zig`) writes it, which is what Ghostty's `+terminal-stream` benchmark reads: each character's length drawn by weight, then a code point uniform over that length's range. `gmixed` is its default (lengths 1-4 at equal weight, ASCII from 0x00), `gfour` four-byte characters only, `gwide` CJK ideographs only (`--weight-wide`), `gwidesp` those with a space after one in ten; cut at 64 B to 64 KiB. `gstream` is 64 KiB of `gmixed`, Ghostty's read size, decoded as its stream decodes: up to each ESC, which with the character after it goes to the parser instead (51 calls, 1.3 KB on average). The earlier corpora (`box`, `latin`, `cjk` with a space every 37 characters, `cjk3` without, `korean`, `japanese`, `cyrillic`, `emoji` with spaces) are still there. Which ghostty-gen options Ghostty's benchmark files used is an assumption: "mixed" as the default and "emoji" as four-byte only.
- Correctness, on the Mac: the package's tests in Debug and ReleaseSafe under Zig 0.17 and 0.16; `just oracle`'s comparison with simdutf 9.3.3 (Homebrew), one million inputs, under simdutf's best kernel and its fallback, with Zig 0.17 and 0.16, and seeds 2-5 with Zig 0.17: 0 mismatches ([apple/oracle-best.txt](apple-utf32-20261105/apple/oracle-best.txt), [apple/oracle-fallback.txt](apple-utf32-20261105/apple/oracle-fallback.txt)); `ab test`, 300 000 inputs through Ghostty's decode against the vendored simdutf, 0 mismatches. On x86-64: `just check` under both Zig versions.

## What changed

0. **Fix: the last byte of a window after three-byte characters** ([steps/fix-window-end-vs-step3.txt](apple-utf32-20261105/steps/fix-window-end-vs-step3.txt)). On the Mac `just oracle` found 11 inputs per converter (`utf8ToUtf16le`, `utf8ToUtf16be`, `utf8ToUtf32`) where `82f0d93` missed an error, reporting the input valid or an error further on ([apple/oracle-base-best.txt](apple-utf32-20261105/apple/oracle-base-best.txt)); the code came with 5266773 (v0.1.0). A block that opens with eight or more three-byte characters and then ASCII decodes in 12-byte windows, each checked by `utf8Invalid(16)`, which checks a byte against the next only inside the 16. The windows' ends came from the block, so a window could see its 16th byte end a character, and `utf8Window`'s path for 16 ends then decoded all 16: a lead there (0xF5, or 0xE1 before ASCII) went unchecked. The window path now passes the ends of the first 15 bytes, as the 16-byte loop's lane mask does. No row moved (0.98-1.01). A test puts each kind of bad byte at every position after such a run; it failed on the Mac before (`want too_short@39 wrote 23, got none@88`).
1. **Blocks of 16 four-byte or 21 three-byte characters first** ([steps/step1-runs-vs-baseline.txt](apple-utf32-20261105/steps/step1-runs-vs-baseline.txt)). The Apple loop found a four-byte block only after validating the whole block and trying the three-byte shapes, and a block of 21 three-byte characters only after the block's end and `utf8AsciiThree`'s tests. Both lead masks are now tested first, and both blocks are checked on their decoded values: a four-byte character is valid when its lead is from 0xF0 and its value from U+10000 to U+10FFFF (the lead keeps four bits, so one from 0xF8 decodes above U+1FFFFF), with the continuation bytes known from the mask; the three-byte run reuses `utf8ThreeRun`. Four-byte characters are packed with two `sli` a lane (`utf8FourApple`), where `utf8DecodeFour` took three masks, three shifts, and three ORs. Neither advance waits on the block's end. `gfour` 64 KiB 2.12x, `gwide` and `cjk3` 1.54-1.57x, `cjk-4096` 1.19x; `gmixed` and `emoji` 0.98 (made up by step 2). The test mixes add `astral`, four-byte characters only, so errors land in that block at every position.
2. **UTF-32 gathered into 32-bit lanes** ([steps/step2-tbl3-vs-step1.txt](apple-utf32-20261105/steps/step2-tbl3-vs-step1.txt), [steps/step2-parity-tables-vs-tbl3.txt](apple-utf32-20261105/steps/step2-parity-tables-vs-tbl3.txt), [steps/step2-pairs-tbl2-vs-parity-20ms.txt](apple-utf32-20261105/steps/step2-pairs-tbl2-vs-parity-20ms.txt)). `utf8DecodeBlock` interleaved the code points' low and high bytes into 16-bit words, and for four-byte characters their top bits into a second set, packed each 8-byte group's words with one `tbl` and the tops with another, then widened both with `ushll`/`shll` and ORed them. On Apple cores the three byte vectors (bits 0-7, 8-15, 16-20) stay apart, and two `tbl`s gather each group's characters straight into 32-bit lanes, with indexes from a 32-byte table entry by the group's mask of ends: from the two low byte registers without four-byte characters (`compress_units`), and from a register of the group's two low bytes, zipped, and the top bytes with them (`compress_pairs`). One `tbl` of three registers: `gmixed` and `emoji` 1.16-1.18x; a table half for each half of a register instead of adding 8 to the index: 1.04-1.05x more; `tbl2` from the zipped pairs for four-byte blocks: 1.04-1.05x more. Without four-byte characters the zipped pairs and a one-register `tbl` were 0.70x (LLVM built the pairs a lane at a time), and `compress_pairs` for both 0.96x, so both tables stay: 32 KiB.
3. **Validation without the fourth-byte test** ([steps/step3-vs-step2.txt](apple-utf32-20261105/steps/step3-vs-step2.txt)). The block tests for a byte from 0xF0 anyway; without one, `utf8InvalidOf(64, false, ...)` leaves out the shift and test for the fourth byte. `box`, `latin`, `korean`, `cyrillic`, `cjk`, `gwidesp` 1.03-1.08x; `gmixed` 0.98-0.99 in that run and 1.005 in the next, with validation before the branch ([steps/step3-one-branch-vs-two.txt](apple-utf32-20261105/steps/step3-one-branch-vs-two.txt)).

## Tried and dropped

- **No windows for UTF-32**, the block decoder for every block with a run of three-byte characters and ASCII, now that it is cheaper ([steps/dropped-no-windows-utf32.txt](apple-utf32-20261105/steps/dropped-no-windows-utf32.txt)): `japanese` 1.08-1.20x, `cjk` 0.86, whose runs are 37 characters long.
- **The block's end before the run tests**, as before step 1 ([steps/dropped-block-end-first.txt](apple-utf32-20261105/steps/dropped-block-end-first.txt)): `cjk3` and `gwide` 0.91, `cjk-4096` 0.89; UTF-16 `emoji` unchanged (1.00), so the order is not what costs it.
- **One table for both block kinds** ([steps/dropped-pairs-tbl1-for-all.txt](apple-utf32-20261105/steps/dropped-pairs-tbl1-for-all.txt), [steps/dropped-pairs-tbl2-for-all.txt](apple-utf32-20261105/steps/dropped-pairs-tbl2-for-all.txt)): above.

## Left

- `gwidesp`, `cjk`, and `japanese`, CJK with spaces or ASCII words, are 1.24-1.62x simdutf from 1 KiB, where runs without them (`gwide`, `cjk3`) are 1.7-1.9x: their blocks go to windows or the block decoder, both vector-bound (by a count of the assembly, a `gmixed` block is about 250 vector operations for 62 bytes, some 70 of them validation).
- Not measured end to end in Ghostty, on a non-virtual Mac, or on M1-M3; the A/B ran on a virtual M4 Pro, where identical builds agree to 0.3% in geomean and rows of 63 bytes move 6% with placement.
