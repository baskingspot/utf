# Runtime ISA dispatch, 2026-10-31

Decision 1 of the plan: can one x86-64 build run the AVX-512, AVX2, SSE, or generic kernels, whichever the CPU has, and what does it cost per call? Measured on `validate.utf8` and `validate.utf8WithErrors`, the first two functions wired through `src/dispatch.zig`.

- Machine: Amp orb, KVM guest, Intel Xeon @ 2.60GHz (Ice Lake server, AVX-512 with VBMI2 and GFNI), 4 vCPUs (2 cores, 2 threads each).
- Zig 0.16.0, ReleaseFast. A scratch testingx suite outside the repository, `bench.zig` and `build.zig` in [dispatch-20261031/](dispatch-20261031/), which takes the package as a consumer does, `b.dependency("utf", .{ .target, .optimize }).module("utf")`, from a path dependency on this tree.
- Inputs: ASCII, Latin, Chinese, and emoji text at 8 B to 64 KiB, valid, 16 bytes past a 64-byte boundary, as in [validate-20261031.md](validate-20261031.md).
- Each arm is one build of the same tree. `run.sh` alternates the four arms run by run in a rotating order, eight rounds, pinned to CPU 3, `--benchtime=200ms`; benchstat compares GB/s (n=8). The raw testingx output is in `raw-<arm>.txt`.

| arm        | build                                                                                          | kernels that run                            |
| ---------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `tier`     | `-Dcpu=x86_64_v4+avx512vbmi+avx512vbmi2+avx512bitalg+avx512vpopcntdq+gfni`, comptime selection | AVX-512, in place                           |
| `dispatch` | `-Dcpu=baseline`, dispatch on by default                                                       | AVX-512, from the AVX-512 object            |
| `native`   | `-Dcpu=native` (`icelake_server`), comptime selection                                          | AVX-512, in place                           |
| `generic`  | `-Dcpu=baseline -Ddispatch=false`                                                              | generic, as every baseline build ran before |

`tier` is the CPU the AVX-512 object is compiled for, so `tier` against `dispatch` is the same kernel code with and without the dispatch.

## Takeaways

- Adopted. A baseline build now runs the AVX-512 kernels on this machine: non-ASCII UTF-8 at 16.5–19.5 GB/s from 1 KiB, against 1.0–2.2 GB/s for the same build without dispatch (8–19×), and within 0–3.4% of a build for the CPU.
- Cost per call: 1.0–1.7 ns for `utf8` and 0.1–1.7 ns for `utf8WithErrors` at 8–64 bytes (a load, a compare, a jump through a table, a tail call into the object, and the object's entry frame). That is 11–24% of `utf8` and 1–10% of `utf8WithErrors` at 8–32 bytes, 5–13% at 256 bytes, 0–3.4% at 1–4 KiB of non-ASCII text, and nothing at 64 KiB. The ASCII rows at 1–4 KiB vary by up to ±35% in both arms and differ by 0–31%.
- Against the generic build, the dispatched build loses only on ASCII of 8–64 bytes (2.5 against 4.0 GB/s at 16 bytes) and long ASCII (51.8 against 61.4 GB/s at 64 KiB). The AVX-512 kernels lose those rows to the generic path even without dispatch (`tier` 3.3 and 51.8 GB/s), so they are the validation kernels' to win back, not dispatch's.
- The AVX-512 tier is compiled for `x86_64_v4` plus VBMI, VBMI2, BITALG, VPOPCNTDQ, and GFNI, and runs only where `cpuid` reports all of them and the OS saves the ZMM state (Ice Lake and later, Zen 4 and later). GFNI is worth 4–10% from 1 KiB: without it the object ran 8–10% behind the `native` build; with it, `tier` and `native` are level (geomean −0.2%).
- Memory: three tier objects with the two wired functions add 21 KB of text (617,009 to 638,145 bytes for the suite) and nothing at run time: peak RSS 1,280 KiB dispatched, 1,296 KiB generic. In ReleaseSafe each object's text is 7.7–8.8 KB, a few KB of it formatting safety-panic messages, which go to the program's panic handler.
- Correctness: `oracle-compare 1000000 1` built with `-Dcpu=baseline`, so every `validate.utf8` call dispatches to the AVX-512 object: 1,638,976 UTF-8 inputs, 0 mismatches in error kind or position for `validate.utf8` and `validate.utf8WithErrors`, under simdutf's `icelake` kernel and again under `fallback`.

## The AVX-512 tier's CPU: GFNI

The first run compiled the AVX-512 object for `x86_64_v4` plus VBMI, VBMI2, BITALG, and VPOPCNTDQ, and that build ran 8–10% behind `native` from 1 KiB on non-ASCII text. Five builds, six rounds, the same rotation (`raw-model-*.txt`, `benchstat-model.txt`): `v4` that CPU, `icelake` `-Dcpu=icelake_server`, `gfni` `v4` plus GFNI, `tuning` `v4` plus Ice Lake's tuning flags (`no_bypass_delay_*`, `tuning_fast_imm_vector_shift`, `ermsb`, `fsrm`), and `native`. GFNI alone closes the gap; the tuning flags do nothing. LLVM shifts bytes with `vgf2p8affineqb` when it has GFNI.

## Candidates

- Per-ISA objects in build.zig, linked into the `utf` module (chosen). `Module.addObject` carries the objects to every artifact that imports the module, so a consumer still writes `b.dependency("utf", ...).module("utf")`. Each object is this package compiled with `src/dispatch.zig` as its root for one tier's CPU; `dispatch.call` in the object `@export`s each wired function, and in the main build it `@extern`s them. Tested: Debug (the main build on the self-hosted backend, the objects on LLVM) and ReleaseSafe at baseline, `x86_64_v2`, and `x86_64_v3`, and a baseline consumer build in ReleaseFast.
- Inline assembly: every kernel written per ISA by hand, which loses `@Vector` and the shared block code. Not pursued.
- Compiling the whole package for a higher CPU: LLVM then uses those instructions everywhere, including the code that must run first to check the CPU. Not viable without a per-function target, which Zig 0.16 lacks.
- Function pointers per function instead of a cached tier and compares: the same load and indirect jump the compiled switch already does (LLVM emits a jump table for the tier compare), so no gain to measure.
