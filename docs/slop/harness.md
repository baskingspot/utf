# Harness

Notes for agents on `bench/`: the comparison benchmarks and the simdutf oracle. `bench/README.md` is the method as a person reads it; this file is how the pieces fit and how to extend them.

## Layout

- `bench/build.zig` and `bench/build.zig.zon`: a Zig build of its own, so the package's build and fetch graph never see the harness. It depends on the package by path (`..`) and on testingx, and installs with `zig build -p ../zig-out`. It builds `bench-std` and `bench-utf` (one source, `bench/zig/arm.zig`, with an `impl` option), `bench-corpus` (`bench/zig/corpus.zig`), and `oracle-compare` (`bench/oracle/compare.zig`), all for the standard `-Dcpu`. `-Dutf-optimize`, `-Dutf-cpu`, and `-Dutf-dispatch` build `bench-utf` (its own instances of the package and testingx) another way, the last as the package's `.dispatch` dependency argument, passed only when set; the justfile's `optimize`, `cpu`, and `dispatch` variables pass them, and `cpu` as `-Dcpu` too, through `bench_zig`, to `bench-corpus` and `bench-build` alike so neither reinstalls the other's arms. `bench-build` builds Rust with `-C target-cpu` into `bench/rust/target/<cpu>/` and Go with `GOAMD64`, from the justfile's `rust_cpu` and `goamd64`, which it derives from `cpu`. `simdutf8` and `base64-simd` detect AVX2 at run time unless built without the Rust arm's `detect` feature, which `bench-build` drops for an x86-64 level or a named CPU (`rust_detect`): a `-C target-cpu=x86-64-v2` build with it still ran AVX2 validation and base64.
- `bench/ops.tsv`: the operations, read at run time by every arm from the repository root: name, row, corpus directory, and output bytes per input byte. `bench/summary.awk`: the per-operation geomean that ends `just bench-compare` and that `just bench-summary` reprints, from per-round paired ratios, with each row's 95% interval in `rows.txt`.
- `bench/simdutf/main.cpp` and `bench/oracle/oracle.cpp`: built by the justfile with the dev shell's `c++` against nixpkgs' simdutf, found with `pkg-config`. Zig's `c++` would bring libc++, which nixpkgs' libstdc++ build of simdutf cannot link with.
- `bench/rust` and `bench/go`: built by the justfile with the flake's toolchains. `Cargo.lock` pins the crates.
- `bench/corpus/`: `sources.tsv` and `SHA256SUMS`. The corpus itself is gitignored in `bench/corpus-gen/`.

## Arm contract

`bench-<arm> bench|check [OP...]` and `bench-<arm> serve`, run from the repository root, with `BENCHTIME_MS`, `BENCH_IN_OFFSET`, and `BENCH_OUT_OFFSET`. `serve` reads `OP INPUT N` lines and answers each with one row: N iterations after one untimed call, or sized to `BENCHTIME_MS` when N is 0; it keeps the last requested operation's inputs and written output buffers loaded and exits at end of input. Every buffer, input or output, is an anonymous mapping of its own (`mmap`, `page_allocator`, `syscall.Mmap`), the input `BENCH_IN_OFFSET` (default 0) bytes into its first page and the output `BENCH_OUT_OFFSET` (default 2048) into its; an arm reads a file straight into its mapping, and takes UTF-16 and UTF-32 code units as views of the bytes, not copies. Row names are `Benchmark<Row>/<input>`; check lines are `<Row>/<input>\t<checksum>`, where the checksum is `valid=<bool>`, `count=<n>`, or `len=<bytes> fnv=<hash>` with UTF-16 and UTF-32 output hashed as its bytes in memory, and the recipe joins them with simdutf's on the name. An arm reads `bench/ops.tsv`, fails if its own table names an operation the file lacks, and prints `# SKIP Benchmark<Row>: <why>` for a listed operation it has no function for. To add an operation, add a line to `bench/ops.tsv`, map its name in each arm that has an equivalent (at least simdutf's and this package's), and add it to `bench/README.md`'s tables; to add an input kind, add a directory to `bench/zig/corpus.zig` and regenerate `SHA256SUMS`, fetched files included: `cd bench/corpus-gen && find . -type f | sort | sed 's|^\./||' | xargs sha256sum > ../corpus/SHA256SUMS`.

`bench-utf` finds the package's functions with `@hasDecl` under the plan's names, from the table in `Utf.api`: `validate.F` and `validate.FWithErrors`, `convert.SToD` and `convert.validSToD` (generated for every pair), `length.*`, and `base64.encode(dst, src, options)` and `base64.decode(dst, src, options)`. `Utf.wrap` adapts each by its signature: one parameter (`bool`, `Result`, or `usize`, a count) validates or counts, two convert (`Result` or `usize` code units written), three are base64. An operation's base64 options set only the fields it names (`alphabet`, `padding`, `last_chunk`) on a value of the function's options type built with `.{}`, so every field needs a default. A function under another name is a skip; one under another signature, or an options type without a field an operation sets, is a compile error in the harness, not a silent skip: fix the arm in the same change.

## Measurement notes

- testingx prints ns/op as a whole number of nanoseconds (`Result.nsPerOp` is an integer), which is a 10–20% step for 16-byte inputs; `serve` prints the Zig arms' rows itself, from the raw total. `bench-compare` feeds benchstat only throughput, converted to GB/s. Raw rows keep ns/op.
- Every arm calls the function out of line, so a loop cannot keep a kernel's constants in registers across calls or fold its setup into the loop: the C++ loop calls into libsimdutf, the Zig loops use `@call(.never_inline, ...)`, Rust calls through a `black_box`ed function pointer, and Go through a function value inside `testing.Benchmark`'s closure. Inlined, `utf`'s 16-byte UTF-8 validation read 3.1 GB/s for a call that costs 10.4 ns, 1.5 GB/s ([harness-fix-20261031.md](results/harness-fix-20261031.md)).
- Each loop iteration first escapes the input pointer with a memory clobber (`doNotOptimizeAway`, `asm volatile`, `black_box`), so a pure call cannot be hoisted out of the loop.
- The Zig arms' wrapped call returns `Out`, a struct whose two fields are computed from the result (`Out.checked`), and the loop keeps only its `n`. A union whose variant the wrapper chose, or a whole-result read, has LLVM store the fields narrow and load them back wide, which cannot forward: about 4–6 ns a call, which a 16-byte row cannot hide ([harness-wave3-20261031.md](results/harness-wave3-20261031.md)). Keep anything new on the timed path built from scalars.
- Peak RSS is GNU time around one `check` pass per arm and operation. The floor is the inputs and output buffers, about 2–14 MiB depending on the operation (UTF-32 inputs are the largest); the rest is runtime.
- Every arm allocates `n * out + 64` bytes of output, from `bench/ops.tsv`, per input, in a mapping of its own. `check` leaves it unwritten, so only the pages an arm writes count in RSS; `bench` and `serve` write the whole mapping before timing. Every arm also writes every page of an input's mapping outside the input, in every mode: an input that ends at a page boundary with a never-touched page after it (4 KiB, 64 KiB, and 1 MiB inputs at offset 0) ran simdutf's `validate_utf16le_with_errors` at 45–48 GB/s on 4 KiB where the old harness's heap buffers gave 125–130, and ours at 132–143 against 164–168, in a first version of this placement. A masked AVX-512 store whose masked-off lanes overhang into a page nothing has written takes a microcode assist on every call, since it never faults the page in; the base64 orb saw simdutf's 4 KiB decode drop from 44 to 21 GB/s that way. No corpus size hit it in this harness, but a new size could. `base64-decode-mime` gets one byte per input byte because Rust's `forgiving_decode` asserts it, compacting the input into the output before decoding there.
- `optimize` and `dispatch` change only `bench-utf`; `cpu` builds `bench-utf`, `bench-std`, Rust (`-C target-cpu`), and Go (`GOAMD64`) for one CPU, so the AVX2 and SSE runs no longer compare against AVX-512 Rust and std; `config.txt` records every arm's build, the buffer offsets, and simdutf's kernel. A `baseline` or `x86_64_v*` build dispatches at runtime unless `dispatch=false`, so on an AVX-512 machine `cpu=x86_64_v3` alone runs the AVX-512 kernels of whatever dispatches; compare with simdutf's `haswell` only with `dispatch=false`.
- On this shared KVM host every arm's throughput steps by up to half for seconds at a time, whatever runs (`Base64Encode/random-4096` in one process: 44, 59, then 44 GB/s; turning off ASLR changed nothing). So `bench-compare` times each row on every arm back to back and takes a row's ratio within each round. Between invocations an arm's own GB/s still moves 17–24% per row; utf ÷ simdutf moves 3.9% (median row) and 1.5% (median operation), against 31.7% and 25% with the old one-arm-at-a-time rounds ([baseline-final-20261031.md](results/baseline-final-20261031.md)). Compare ratios within a run, not GB/s across runs.
- The timed loops cost the same in every arm: a call to a function that returns at once costs 1.41 ns in the C++ loop (through the PLT, as libsimdutf is called), 1.25 in the Zig loop (`b.loop()` is itself an out-of-line call per iteration), 1.24 in Rust's, and 1.33 in Go's.
- Code layout is not controlled: identical code at another address moved rows ±15% in wave 3, and a run's intervals do not include it.
- A full run (66 operations, 877 rows for simdutf and this package, 156 for std, 248 for Rust, 141 for Go) takes about 26 minutes for 10 rounds at 50 ms a sample on the 4-vCPU orb.
- `base=<rev>` is an A/B in one run: `bench-build` extracts the revision with `git archive` into `zig-out/base/tree`, builds its own `bench/` with the same `bench_flags`, and installs its `bench-utf` as `bench-base`, which runs from this tree's root with this tree's `ops.tsv` and corpus. The summary's `base` column is utf ÷ base per round. A revision whose arm names an operation this `ops.tsv` lacks fails its check.
- No orb is aarch64. `.github/workflows/bench.yml` runs `bench-compare` (with `base` if given) on a GitHub-hosted runner, `ubuntu-26.04-arm` by default, and uploads `zig-out/bench-compare` with `lscpu.txt`: `gh workflow run bench.yml -R baskingspot/utf --ref <branch> -f base=<rev> -f ops='validate-utf8 utf8-to-utf16le'`, then `gh run download`. The branch must be on GitHub; hosted runners are shared VMs, so read the ratios, not the GB/s.

## Oracle

Protocol (little endian): request `u8 op, u8 option, u32 len, bytes`; response `u8 error, u64 count, u32 len, bytes`. The oracle reads all of stdin before it writes, so a client writes a whole batch, closes stdin, and reads. `Oracle.run` does that and spawns once per batch; use batches of thousands. Op numbers are the `Oracle.Op` enum. simdutf honors `SIMDUTF_FORCE_IMPLEMENTATION` (`fallback`, `haswell`, `icelake`, ...), which `just oracle` uses to check the scalar kernel too.

simdutf's error codes match `src/result.zig`'s `Error` by name except for ASCII, where simdutf says `TOO_LARGE` and the package says `not_ascii`. `Oracle.run` renames `validate_ascii`'s `too_large` to `Oracle.Error.not_ascii`, a value simdutf never sends, so `Oracle.sameError` matches every kind by name.

`bench/oracle/compare.zig` has a table of checks per input kind (UTF-8, ASCII, UTF-16LE, UTF-16BE, UTF-32, Latin-1, base64, and binary for the encoder), each with its generator. `check(ns, name, op, extra)` makes one from a function of ours and the oracle op it is held against, and picks the comparison from the signature as `bench-utf`'s `Utf.wrap` does: `(src) bool` on validity; `(src) Result`, `(src, dst) Result`, and the base64 functions on kind, position, and output; `(src) usize` (a length) and `(src, dst) usize` (a valid form) only where simdutf accepts, against the count and output of the conversion they size or mirror. `extra` sets base64 options, from which `check` derives simdutf's option byte, and `.swapped` for the UTF-16 byte swaps, held against validation with the byte-swapped input as the expected output, since the oracle has no `change_endianness_utf16`. One that does not exist yet is skipped. A batch sends one request per input for each distinct op and option, however many checks share it. The first mismatch of each check is shrunk by removing runs of code units, halved down to one, through the oracle, and printed with both answers. The `std.*` checks hold Zig's std against simdutf so the plumbing has a second, independent client. The default-options base64 checks assume the package's defaults mean simdutf's: the standard alphabet, loose last chunk, whitespace skipped. To fuzz a new function against simdutf, add a `check` to its kind's table; for one-off use, import `Oracle` from a program in the bench build.

At the default N, `just oracle` makes 27 million comparisons in 82 checks per kernel, about 1 minute 45 seconds each on two of the orb's vCPUs. It compares the package as built for the host, so on an AVX-512 machine it checks the AVX-512 kernels only. Not compared: `base64.encodedLen` and `maxDecodedLen`, the per-ISA `encodeWith` and `decodeWith`, the `scalar` modules other than `validateUtf8`, and `output_buffer_too_small`, since simdutf's checked conversions take no output length.

## Results so far

- `results/baseline-20261030.md`: simdutf, std, Rust, and Go on the whole corpus, and the oracle against `scalar.validateUtf8` (no mismatches).
- `results/harness-fix-20261031.md`: the out-of-line calls and written output buffers, old harness against new; `utf`'s and Rust's 16–256-byte rows were overstated by up to 2×.
- `results/baseline-20261031.md`: every operation, after wave 1 and runtime dispatch: the native build against simdutf's `icelake` and the AVX2 build against `haswell`, with the gap per operation.
- `results/harness-wave3-20261031.md`: `Out` built from scalars, old harness against new: the checked conversions' 16–64-byte rows 2–3.5 ns a call faster, short base64 decodes 4–8 ns; and `just oracle` on every public function, with no mismatches.
- `results/baseline-final-20261031.md`: the paired-round harness (run-to-run noise 25% to 1.5% per operation), and the final baseline of every operation and arm at native, AVX2, SSE, dispatched baseline, and ReleaseSafe, with the rows under 1.0 outside the noise and peak RSS.
